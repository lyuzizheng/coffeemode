# 0004. Server Structured Errors + Request-ID

## Status

Accepted

## Context

`web/app/api` + `web/lib` had 30+ hand-written `console.error("…failed", err)` calls with inconsistent copy, no level, and no correlation key. The BRAWUKA-167 access log (`web/proxy.ts`, one JSON line per request) could not be joined to error lines, so a production 500 could not be traced from access log to cause. No SaaS log service is wanted — Cloudflare Observability already covers the edge.

## Decision

request-id is generated by the proxy (`web/proxy.ts`) and forwarded on request headers; route handlers read it via `getRequestId(request)` and fall back to `crypto.randomUUID()` when missing/invalid (notably `/api/health`, which the proxy matcher skips). A valid inbound `x-request-id` is reused, anything else regenerated; the final value is echoed on the response. Trust boundary: `request_id` is a log-correlation key only — client-supplied values are never a trust signal and must not feed authorization or dedup decisions. Errors log one JSON line via `logError({ route, requestId, error, status? })` (`web/lib/observability/server-log.ts`, `type: "error"` joining `type: "access"` on `request_id`). Only `message` + first stack frame are recorded — never whole error objects or request bodies.

## Consequences

- Every 500/502/upstream failure is greppable by `request_id` across access + error lines with no new dependency.
- Lib code without request context logs `request_id: null` (structured but uncorrelated) — accepted; the route handler's own catch carries the id.
- `poi-service`/`image-service` workers are untouched; cross-service correlation is a follow-up.
